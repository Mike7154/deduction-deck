# Clue Strategy Simulation Research Design

## Purpose

This project studies suggestion-selection strategies for Clue/Cluedo using a solver-backed simulator. The core question is:

> Which suggestion strategy minimizes the number of turns needed for a player to solve the envelope, and how do strategy performance, information leakage, player count, and turn-order position interact?

The simulator currently supports experiments where one focal player ("Me") uses a specified strategy while opponents follow a semi-random behavioral model. It is designed to be extended later to all-players-strategic simulations where every player has their own knowledge state and strategy.

## Code Locations

- App solver: `src/solver.ts`
- Simulation engine: `src/simulation.ts`
- Simulation CLI: `scripts/run-simulation.ts`
- Analysis CLI: `scripts/analyze-simulation.ts`
- Run simulation: `npm run simulate`
- Analyze CSV output: `npm run analyze`

The simulator is separate from the UI. It is not imported by `src/App.tsx`, so it is currently a research/testing tool, not an in-app feature.

## Current Game Model

### Deck and Rules

The simulator uses the standard app deck:

- 6 suspects
- 6 weapons
- 9 rooms
- 21 total cards
- Envelope contains exactly 1 suspect, 1 weapon, and 1 room

Supported player counts:

- 3 players: 18 non-envelope cards are dealt evenly as 6 cards/player
- 6 players: 18 non-envelope cards are dealt evenly as 3 cards/player

### Dealing

For each simulated trial:

1. Randomly choose one suspect, one weapon, and one room for the envelope.
2. Shuffle the remaining 18 cards.
3. Deal evenly to the selected number of players.
4. Assign one player as the focal player, "Me".

The simulator uses seeded pseudo-randomness, making experiments reproducible.

### Knowledge State

The focal player starts with direct knowledge of their own hand:

- Own cards are marked `YES` for Me.
- Non-own cards are marked `NO` for Me.

Evidence from suggestions is added to a `GameState`, then evaluated by the same solver used by the web app: `solveGame(...)`.

### Solver

The solver enumerates valid deals consistent with:

- hard yes/no marks,
- card counts per player,
- one envelope card per category,
- suggestion evidence,
- unknown-card disproof clauses.

It returns:

- probabilities for each card/location,
- envelope picks,
- accusation probability,
- deductions,
- valid-world count.

## Opponent Model

Current experiments are focal-player experiments. Opponents do not each maintain independent private solvers. Instead, opponent suggestions are generated by a semi-random behavioral model:

- Opponents choose one suspect, one weapon, and one room.
- They prefer cards not known to be held by someone else.
- They sometimes choose cards from their own hand.
- They avoid suggesting all three cards from their own hand.

This opponent model is intended as a plausible baseline, not a claim about optimal human play.

## Suggestion Resolution

For a suggestion:

1. Players are checked in turn order after the suggester.
2. The first player who holds at least one suggested card disproves.
3. If the focal player is the asker or disprover, the exact shown card is recorded.
4. If another player disproves another player's suggestion, only an unknown-card clause is recorded.
5. If nobody disproves, all intervening players are marked unable to hold all three suggested cards.

## Experimental Design

### Paired / Blocked Design

The simulator now supports paired trials by default.

In paired mode, each trial uses the same base random seed/deal across all strategies. Thus, strategy comparisons are blocked by game instance. This controls for major game-difficulty variance from:

- envelope composition,
- focal player's hand,
- opponents' hands,
- initial random conditions.

Paired mode is the default:

```bash
npm run simulate -- --games=100 --strategies=likely,random,privateInfo
```

Unpaired mode can be run with:

```bash
npm run simulate -- --games=100 --paired=false
```

### Turn-Order Position Control

Turn order is treated as a potential confounder.

Fixed focal position:

```bash
npm run simulate -- --games=500 --playerCount=6 --myPosition=0
```

Randomized focal position:

```bash
npm run simulate -- --games=500 --playerCount=6 --myPosition=random
```

Sweep all positions:

```bash
npm run simulate -- --games=500 --playerCount=6 --positionSweep=true
```

Recommended robustness checks:

```bash
npm run simulate -- --games=500 --playerCount=6 --positionSweep=true --out=sim-6p-positions.csv
npm run simulate -- --games=500 --playerCount=3 --positionSweep=true --out=sim-3p-positions.csv
```

### Player Count Control

The primary planned player-count conditions are:

- 3 players
- 6 players

These are emphasized because 18 non-envelope cards divide evenly in both cases.

## Strategies Currently Implemented

### Static / Baseline Strategies

#### `likely`

Always suggests the current most likely envelope combination according to the solver:

- most likely suspect,
- most likely weapon,
- most likely room.

This is the primary baseline.

#### `random`

Randomly chooses one currently plausible envelope candidate per category. This is a baseline to test whether engineered strategies outperform non-optimized play.

#### `balanced`

Attempts to balance category progress. If a category is nearly solved or low-entropy, it may use one of Me's own cards in that category as an anchor, allowing the suggestion to pressure other categories.

#### `infoGain`

Uses a heuristic estimate of response information gain. It favors suggestions expected to produce informative response patterns and shown-card uncertainty reduction.

#### `hybrid`

Uses `likely` when accusation probability is above a threshold; otherwise uses `infoGain`.

### Pass / Target Strategies

#### `passNext`

Attempts to choose cards unlikely to be held by the next player, increasing the chance the suggestion passes to later players.

#### `passMany`

A stronger pass-through variant, trying to maximize pass-through and nobody-disproved signals.

#### `targetNext`

Attempts to choose cards likely to be held by the next player, increasing immediate disproof and exact-card opportunities.

#### `privateInfo`

Values immediate disproof and exact shown-card information while penalizing table-wide leakage from pass-through.

### Hybrid / Weighted Strategies

#### `weightedInfo`

Weighted score combining:

- information value,
- bottleneck pressure,
- exact shown-card value,
- self-card probe value,
- envelope pressure,
- table leakage penalty.

It uses a lighter privacy penalty than `weightedPrivate`.

#### `weightedPrivate`

Same score structure as `weightedInfo`, but with a stronger leakage penalty.

#### `phaseHybrid`

Changes strategy based on game state:

- high accusation probability: use `likely`,
- late-game low uncertainty: use `decisiveProbe`,
- imbalanced category uncertainty: use weighted bottleneck pressure,
- otherwise use weighted/info-private logic.

#### `decisiveProbe`

Late-game strategy that values suggestions where a nobody-disproved result may directly solve the envelope, especially when one or more categories are anchored by Me's own cards.

### Tunable Parameters

The simulator exposes several parameters for testing strategy variants. These parameters primarily affect the weighted strategies:

- `weightedInfo`
- `weightedPrivate`
- `phaseHybrid`
- `decisiveProbe` for decisive no-disprove logic

Static strategies such as `likely`, `random`, `balanced`, `targetNext`, `passNext`, and `passMany` are mostly unaffected except where explicitly noted.

Default values:

```text
infoWeight             = 1
bottleneckWeight       = 0.08
exactWeight            = 0.35
selfProbeWeight        = 0.35
leakageWeight          = 0.25
envelopeWeight         = 0.15
decisiveNobodyWeight   = 1.1
lateLeakageDiscount    = 0.35
targetPasses           = 1.5
targetPassWeight       = 0
suspectWeight          = 1
weaponWeight           = 1
roomWeight             = 1
accusationThreshold    = 0.88
```

#### `infoWeight`

Controls the value placed on broad expected information from a suggestion. Higher values favor moves with uncertain/informative response patterns, even if they are not the currently most likely accusation.

Example:

```bash
npm run simulate -- --games=200 --infoWeight=1.4
```

#### `bottleneckWeight`

Controls how much the strategy pressures categories with larger remaining uncertainty. A higher value should encourage solving the slowest category rather than repeatedly testing already-narrow categories.

Example:

```bash
npm run simulate -- --games=200 --bottleneckWeight=0.12
```

#### `exactWeight`

Controls the value placed on getting an exact shown card. Higher values favor suggestions likely to be disproved by an early player, especially when the shown card would be informative.

Example:

```bash
npm run simulate -- --games=200 --exactWeight=0.55
```

#### `selfProbeWeight`

Controls the value of using Me's known cards as anchors. Increasing this encourages suggestions like "my known suspect + uncertain weapon + uncertain room" when trying to isolate information in unsolved categories.

Example:

```bash
npm run simulate -- --games=200 --selfProbeWeight=0.6
```

#### `leakageWeight`

Controls the penalty for giving information to the table. Higher values discourage suggestions that pass through many players or create public no-disprove signals. Lower values prioritize focal-player solve speed over privacy.

Examples:

```bash
# More private
npm run simulate -- --games=200 --leakageWeight=0.45

# More aggressive/public
npm run simulate -- --games=200 --leakageWeight=0.1
```

#### `envelopeWeight`

Controls how much the strategy favors cards already likely to be in the envelope. Higher values make weighted strategies behave more like `likely`.

Example:

```bash
npm run simulate -- --games=200 --envelopeWeight=0.45
```

#### `decisiveNobodyWeight`

Controls the late-game value of suggestions where a nobody-disproved response may directly solve the envelope. This is intended to model the intuition that public no-disprove signals are acceptable if they give Me the answer immediately or nearly immediately.

Example:

```bash
npm run simulate -- --games=200 --decisiveNobodyWeight=1.8
```

#### `lateLeakageDiscount`

Reduces the leakage penalty in late-game states. A value of `0` means leakage is penalized equally at all stages. Higher values mean public information is treated as less costly when the focal player is close to solving.

Example:

```bash
npm run simulate -- --games=200 --lateLeakageDiscount=0.6
```

#### `targetPasses` and `targetPassWeight`

The weighted strategies can optionally prefer a specific expected number of players to pass before disproof.

- `targetPasses` is the desired expected pass-through count.
- `targetPassWeight` controls how strongly the strategy is penalized for being above or below that target.

By default this is disabled because `targetPassWeight = 0`.

This directly tests whether it is better to avoid cards likely held by the next player, target the next player, or aim for an intermediate amount of pass-through.

Examples:

```bash
# Prefer about one player passing before disproof
npm run simulate -- --games=200 --targetPasses=1 --targetPassWeight=0.2

# Test deeper pass-through / avoiding next players
npm run simulate -- --games=200 --targetPasses=2.5 --targetPassWeight=0.3

# Prefer near-immediate disproof
npm run simulate -- --games=200 --targetPasses=0.25 --targetPassWeight=0.3
```

#### `suspectWeight`, `weaponWeight`, and `roomWeight`

These category weights let the weighted strategies prioritize one card category over another.

They multiply:

- bottleneck pressure,
- envelope pressure,
- self-probe value,
- decisive no-disprove value.

Because rooms often appear to solve last, `roomWeight` can be increased to test whether forcing room pressure improves average solve time or tail behavior.

Examples:

```bash
# Mild room priority
npm run simulate -- --games=200 --roomWeight=1.5

# Strong room priority with less general bottleneck pressure
npm run simulate -- --games=200 --roomWeight=2.0 --bottleneckWeight=0.06

# Compare category priorities explicitly
npm run simulate -- --games=200 --suspectWeight=1 --weaponWeight=1 --roomWeight=1.75
```

#### `accusationThreshold`

Controls when hybrid strategies switch to the `likely` accusation-testing behavior. If the solver's current best accusation probability exceeds this threshold, hybrid strategies tend to stop probing and test the likely answer.

Example:

```bash
npm run simulate -- --games=200 --accusationThreshold=0.8
```

### Example Combined Tuning Runs

More `likely`-like weighted behavior:

```bash
npm run simulate -- --games=200 --strategies=likely,weightedInfo,weightedPrivate,phaseHybrid,random \
  --infoWeight=0.6 \
  --bottleneckWeight=0.03 \
  --exactWeight=0.25 \
  --selfProbeWeight=0.15 \
  --leakageWeight=0.25 \
  --envelopeWeight=0.45 \
  --decisiveNobodyWeight=0.4
```

Room-priority bottleneck test:

```bash
npm run simulate -- --games=200 --strategies=likely,weightedInfo,phaseHybrid,random \
  --roomWeight=1.75 \
  --bottleneckWeight=0.08 \
  --targetPasses=1.5 \
  --targetPassWeight=0.1
```

Private late-game strategy test:

```bash
npm run simulate -- --games=200 --strategies=likely,weightedPrivate,privateInfo,decisiveProbe,random \
  --leakageWeight=0.45 \
  --lateLeakageDiscount=0.5 \
  --decisiveNobodyWeight=1.4
```

## Metrics Reported

### Primary Metric

- Turns to solve the envelope for the focal player.

The report includes:

- mean turns,
- standard deviation,
- approximate 95% confidence interval,
- median,
- IQR,
- P95,
- mean rank in paired trials.

### Secondary / Exploratory Metrics

- average focal-player turns,
- average pass-through count per suggestion,
- approximate no-facts gained per suggestion,
- immediate disproof rate,
- nobody-disproved rate,
- exact shown cards per game,
- entropy imbalance across suspect/weapon/room categories,
- average solve turn for each category: suspect / weapon / room,
- average solver worlds.

### Trial-Level CSV Fields

CSV output includes:

```text
trial, seed, strategy, playerCount, myPosition, solved, turns, myTurns,
suspectSolvedTurn, weaponSolvedTurn, roomSolvedTurn,
mySuggestions, passCount, noFacts, immediateDisproofs,
nobodyDisproved, exactShownToMe, entropyImbalance, averageSolverWorlds
```

## Statistical Analysis Plan

The analysis is inspired by Demšar (2006), "Statistical Comparisons of Classifiers over Multiple Data Sets," treating each simulated game/deal as a paired data set and each strategy as a classifier/algorithm.

### Primary Analysis

Use paired non-parametric comparisons because turn counts are discrete, right-skewed, and not normally distributed.

Planned tests:

1. Friedman test as omnibus test across strategies.
2. Pairwise Wilcoxon signed-rank comparisons against the best mean-rank strategy or a pre-declared baseline such as `likely`.
3. Holm-Bonferroni correction for multiple comparisons.
4. Effect size via rank-biserial correlation.

The current `npm run analyze` script provides:

- summary table,
- mean ranks,
- Friedman chi-square statistic,
- pairwise Wilcoxon signed-rank approximation,
- Holm threshold,
- rank-biserial effect size.

It does not currently compute exact Friedman p-values or Nemenyi critical-difference diagrams. For publication, export CSV and perform final statistics/plots in R or Python.

Suggested external tools:

- R: `PMCMRplus`, `scmamp`, `coin`, `rstatix`
- Python: `scipy.stats.friedmanchisquare`, `scipy.stats.wilcoxon`, `scikit-posthocs`, Orange CD diagram utilities

### Effect Sizes and Practical Significance

With large `n`, small differences may become statistically significant but not practically important. Report both:

- p-values / adjusted p-values,
- median difference in turns,
- rank-biserial effect size,
- P95 tail behavior.

## Current Observations / Working Hypotheses

Preliminary unpaired and small paired runs suggest:

1. `likely` is a strong baseline and may outperform more elaborate heuristics.
2. `random` sometimes performs surprisingly close to engineered strategies.
3. Pass-heavy strategies (`passNext`, `passMany`) often perform poorly despite generating many no-facts.
4. Strategies overvaluing nobody-disproved/pass-through can have worse tail behavior.
5. Category solve decomposition may reveal bottlenecks hidden by aggregate turn count.
6. Turn-order position is likely a confounder and should be explicitly controlled.

The surprising competitiveness of `random` and `likely` is itself an important research finding. It may imply that:

- the solver extracts most useful information regardless of focal strategy,
- opponent turns dominate evidence gain,
- testing the most likely solution is already near-optimal under the current model,
- or current heuristic proxies do not align well with actual solve time.

## Limitations

1. Opponents do not maintain independent private solvers.
2. Opponent behavior is heuristic, not calibrated from human data.
3. Current simulator studies focal-player solve time, not actual game win rate.
4. The analysis script uses approximate normal methods for Wilcoxon p-values.
5. No current all-players-strategic equilibrium simulation exists.
6. Runtime can be high because the real solver is called repeatedly.

## Planned Extension: All-Players-Strategic Simulation

A future experiment should simulate every player using the same or different strategies, each with a private knowledge state. This would answer:

- How long does the whole game last?
- Which turn-order position wins most often?
- Does the best focal-player strategy remain best when everyone uses it?
- How do 3-player and 6-player games differ?

This requires maintaining separate `GameState`/evidence for each player and deciding what each player observes from every suggestion.

## Questions for External Review

1. Is the paired/blocking design sufficient for controlling game difficulty?
2. Should turn-order position be treated as a blocking factor, covariate, or separate subgroup analysis?
3. Are Friedman + Wilcoxon/Holm appropriate, or should mixed-effects models be added?
4. Should the primary outcome be focal-player solve turn, accusation turn, or win probability?
5. How should public information leakage be modeled and valued?
6. Does the opponent heuristic model introduce bias favoring `likely` or `random`?
7. What sample size is appropriate to detect 0.5-turn and 1-turn differences?
8. Should final analysis use mean rank/CD diagrams, mixed models, or both?
